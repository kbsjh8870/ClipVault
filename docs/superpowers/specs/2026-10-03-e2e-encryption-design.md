# 종단간 암호화(E2E) — 설계

- 작성일: 2026-10-03
- 상태: 설계 승인됨, 스펙 검토 중
- 대상 버전: 백엔드(main 머지 시 자동 배포), 트레이 앱 v1.6.0
- 관련 문서: PRD.md, TRD.md, API_CONTRACT.md

## 1. 목표와 범위

클립 내용(텍스트, 이미지 원본, 썸네일)을 **트레이 앱에서 암호화**해서 올리고, 받은 앱에서만 푼다.
서버·DB·버킷이 유출되어도 내용은 암호문뿐이게 한다. 지금은 서버가 AES 키(`CLIP_ENCRYPTION_KEY`)를 들고 있어서 VM이 털리면 전부 읽힌다.

- 모든 사용자에게 필수다. 업데이트 후 볼트 암호를 만들거나 입력해야 동기화가 계속된다.
- 기존 동작(알림 후 클릭 시 반영, 중복 방지, 검색, 고정, 보관 기간, 더 보기, 실시간 추가)은 그대로다.
- 서버 암호화로 저장된 기존 클립은 앱이 종단간 암호화로 옮긴다(데이터 손실 없음).

**범위 밖**
- 메타데이터 숨기기 (시각, 기기, 종류, 크기, 이미지 가로세로, 고정 여부는 서버가 계속 본다)
- 복구 코드, 기기 간 키 전달(QR 등)
- 서버 AES 키 제거 (옛 행이 0개가 된 뒤 별도 작업)

## 2. 결정 사항

| 항목 | 결정 | 이유 |
|---|---|---|
| 키 출처 | 로그인과 별도인 **볼트 암호** | 로그인 구조를 그대로 둔다. 로그인 비밀번호에서 만들면 서버가 비밀번호를 받으므로 서버도 키를 만들 수 있다 |
| 키 구조 | **봉투 암호화**: 무작위 볼트 키(VK)를 암호에서 만든 잠금 키(KEK)로 감싸 서버에 보관 | 암호 변경 = 다시 감싸기만, 클립 재암호화 없음. 다른 PC 영향 없음 |
| 적용 | 모든 사용자 필수 | 코드 경로 하나. 서버가 볼트 있는 사용자의 평문 업로드를 거부할 수 있다 |
| 암호 변경 / 분실 | 변경 = 다시 감싸기(클립 보존) / 분실 = 초기화(모든 클립 삭제 후 새 키) | 클립은 최대 30일이면 사라지는 데이터라 분실 비용이 작다 |
| PC 저장 | 볼트 키를 윈도우 DPAPI로 잠가 Preferences에 저장, PC마다 처음 한 번만 입력 | 자동 실행·지금의 사용감 유지. 로그아웃하면 지운다 |
| 기존 데이터 | 앱이 받아서 암호화해 같은 자리에 덮어씀 | 손실 없음. 끝나면 서버는 내용을 전혀 못 본다 |
| 암호 알고리즘 | PBKDF2-HMAC-SHA256 + AES-256-GCM + HMAC-SHA256 (모두 JDK 표준) | 의존성 추가 없음 |

## 3. 키와 데이터 형식

### 3.1 키

| 키 | 만드는 법 | 위치 |
|---|---|---|
| 볼트 키 VK | `SecureRandom` 32바이트, 사용자당 하나 | 서버(감싼 형태), 각 PC(DPAPI) |
| 암호화 키 | `HMAC-SHA256(VK, "clipvault-enc-v1")` | 메모리 |
| 해시 키 | `HMAC-SHA256(VK, "clipvault-hash-v1")` | 메모리 |
| 잠금 키 KEK | `PBKDF2WithHmacSHA256(볼트 암호, salt, iterations, 256bit)` | 메모리 (만들고 바로 버림) |

- salt: 16바이트 무작위. iterations: 새로 만들 때 600,000. 앱은 서버가 준 값을 쓰되 **100,000 미만이면 거부**한다.
- 감싼 볼트 키 `wrappedKey` = `base64(IV 12 ‖ AES-GCM(KEK, VK, AAD))`, AAD = `"clipvault-vault-v1:" + userId`.
  다른 사용자의 감싼 키로 바꿔치기하면 태그 검증에 실패한다. 틀린 암호도 태그 검증 실패로 알 수 있다.

### 3.2 클립 데이터

모두 암호화 키로 AES-256-GCM, 매번 무작위 12바이트 IV, 형식은 `IV ‖ 암호문 ‖ 태그`.

| 대상 | 평문 | AAD | 서버 저장 |
|---|---|---|---|
| 텍스트 | UTF-8 바이트 | `text-v1` | `clips.content` = base64(형식) |
| 이미지 원본 | PNG 바이트 | `image-v1` | 버킷 `images/{key}` = 형식 바이트 그대로 |
| 썸네일 | PNG, 앱이 생성(긴 변 240px, 원본이 작으면 원본 크기) | `thumb-v1` | 버킷 `thumbs/{key}` = 형식 바이트 그대로 |

- AAD가 달라서 서버가 원본/썸네일/텍스트를 바꿔치기하면 복호화에 실패한다.
- 이미지 클립의 `content`는 빈 문자열이다(가로세로는 `width`/`height` 컬럼).

### 3.3 중복 판별 해시

`contentHash = hex(HMAC-SHA256(해시 키, 평문 바이트))` (텍스트는 UTF-8, 이미지는 업로드하는 PNG 바이트).
같은 내용이면 같은 값이라 서버의 "직전 클립과 같으면 시각만 갱신"이 그대로 동작하고,
서버는 해시 키가 없어 짐작한 평문과 대조(사전 공격)할 수 없다.

## 4. 서버

### 4.1 데이터

`users`에 추가 (볼트 설정 전에는 null, `ddl-auto: update`로 추가):

| 컬럼 | 타입 | 설명 |
|---|---|---|
| vault_salt | varchar(32), null | base64 salt |
| vault_iterations | int, null | PBKDF2 반복 횟수 |
| vault_wrapped_key | varchar(128), null | base64 감싼 볼트 키 |
| vault_version | int, 기본 0 | 초기화할 때마다 +1. 0 = 볼트 없음 |

`clips`에 추가:

| 컬럼 | 타입 | 설명 |
|---|---|---|
| e2e | boolean, 기본 false | true = 앱이 암호화한 행(서버는 그대로 저장/반환), false = 서버 암호화한 옛 행 |

### 4.2 볼트 API (device 토큰 필수)

| 요청 | 응답 |
|---|---|
| `GET /api/vault` | `200 {salt, iterations, wrappedKey, version}` / 볼트 없음 `404` |
| `POST /api/vault {salt, iterations, wrappedKey}` | `201 {version: 1}` / 이미 있음 `409` |
| `PUT /api/vault {salt, iterations, wrappedKey, version}` | `204` 다시 감싸기(암호 변경) / version 불일치 `409` / 볼트 없음 `404` |
| `POST /api/vault/reset {salt, iterations, wrappedKey}` | `200 {version}` 그 사용자의 클립 행과 버킷 객체를 모두 지우고 새 키 저장, version +1 |

- 입력 검사: salt는 base64 16바이트, iterations ≥ 100,000, wrappedKey는 base64 (12 + 32 + 16 = 60바이트). 아니면 `400`.

### 4.3 업로드 규칙 (`X-Vault-Version` 헤더)

| 헤더 | 사용자 볼트 | 처리 |
|---|---|---|
| 없음 | 없음 | 옛 방식 그대로 (구버전 앱 호환: 서버가 평문 받아 서버 암호화, `e2e=false`) |
| 없음 | 있음 | `426 Upgrade Required` "앱을 업데이트하세요" |
| 있음, 현재 version과 같음 | 있음 | e2e 업로드 (아래) |
| 있음, 다름 (또는 볼트 없음) | — | `409` "볼트가 바뀌었습니다" |

- **텍스트** `POST /api/clips {content, contentHash}` (e2e)
  - content: base64, 디코딩 길이 ≤ 12 + 300,000 + 16 (평문 10만 자 × UTF-8 최대 3바이트). contentHash: 소문자 hex 64자. 아니면 `400`.
  - 서버 암호화 없이 그대로 저장, `e2e=true`. 중복 판별·푸시 동작은 기존과 같다.
- **이미지** `POST /api/clips/image` (e2e, `multipart/form-data`)
  - 파트: `image`(암호문 바이트), `thumb`(암호문 바이트), `width`, `height`, `contentHash`.
  - 크기: image ≤ 10MB + 28바이트, thumb ≤ 1MB, 넘으면 `413`. width·height는 1 이상, 곱이 5천만 이하, 아니면 `400`.
  - PNG 검사·썸네일 생성 없이 받은 바이트를 그대로 버킷에 저장(서버 암호화 없음). 저장 순서와 실패 처리(버킷 먼저, DB 실패 시 객체 삭제, `503`)는 기존과 같다.
  - 중복(직전 이미지와 해시 같음)이면 기존처럼 객체를 다시 쓰고 시각 갱신 `200`.
- 옛 방식 업로드 경로(헤더 없음 + 볼트 없음)는 지금 코드를 그대로 둔다.

### 4.4 조회

- `ClipResponse`에 `e2e` 추가. e2e 행은 `content`를 저장된 암호문 그대로, 옛 행은 지금처럼 서버가 복호화한 평문으로.
- `GET /api/clips/{id}/image`, `/thumbnail`: e2e 행은 저장된 바이트(암호문) 그대로, 옛 행은 지금처럼 복호화.
- `GET /api/clips?legacy=true`: `e2e=false`인 내 클립(고정 포함)을 최신순으로 최대 100개. limit/before/pinned 무시.
- 실시간 푸시도 같은 `ClipResponse`.

### 4.5 기존 데이터 이전 API

`PUT /api/clips/{id}/e2e` (`X-Vault-Version` 필수, 규칙은 4.3과 같음)
- 텍스트 클립: JSON `{content, contentHash}`. 이미지 클립: multipart `image`, `thumb`, `contentHash` (검사는 4.3과 같음).
- 이미 `e2e=true`면 아무것도 안 하고 `204` (두 PC가 동시에 이전해도 안전).
- id, created_at, expires_at, pinned, source_device_id, width/height는 그대로. content·content_hash를 바꾸고 `e2e=true`.
- 이미지는 같은 버킷 키에 암호문을 **먼저** 덮어쓰고 DB를 바꾼다. 버킷 쓰기 실패 시 `503`, 행은 옛 상태 그대로.
- 남의 클립 `404`.

### 4.6 그대로 두는 것

고정·보관 기간·정리 배치·고정 이미지 재작성(`renewPinnedImages`)은 버킷 객체를 내용과 무관한 바이트로 다루므로 바뀌지 않는다.
서버 AES 키(`CLIP_ENCRYPTION_KEY`)는 옛 행을 읽기 위해 남긴다. 정리 배치가 매일 옛 행 개수를 로그에 남긴다.

## 5. 트레이 앱

### 5.1 새 부품

- `crypto/VaultCrypto`: 키 생성, KEK 유도, 감싸기/풀기, 하위 키, 텍스트/바이트 암복호화, HMAC 해시. 순수 함수 위주(단위 테스트 대상).
- `crypto/Vault`: 이 PC의 볼트 상태(볼트 키, version) 보관. DPAPI(`Crypt32Util.cryptProtectData/UnprotectData`)로 잠가 Preferences에 저장/로드/삭제.
- `ui/VaultDialog`: 만들기, 입력, 변경, 초기화 확인 창 (로그인 창과 같은 스타일).
- `clipboard/Images`에 썸네일 생성 추가 (서버 `ImageBytes`의 축소 로직을 옮김: 긴 변 240px, 비율 유지).

### 5.2 볼트 확인 (`ensureVault`)

로그인 직후, 앱 시작(로그인 상태), WebSocket 재연결 시 `GET /api/vault`:

| 상황 | 동작 |
|---|---|
| 404 | **만들기** 창 → VK·salt 생성, 감싸서 `POST` → 저장 → 5.6 이전 |
| 있음, 이 PC에 키 없음 | **입력** 창 → 풀기 → 저장 → 5.6 이전 |
| 이 PC 키의 version ≠ 서버 version | "다른 PC에서 볼트가 초기화되었습니다" + **입력** 창 |
| 키 있고 version 같음 | 사용 → 5.6 이전(옛 행 남았으면) |
| 네트워크 오류 | 저장된 키로 계속(있으면). 나중에 409를 받으면 입력 창 |

- 만들기: 암호·확인, 8자 이상, "잊으면 클립을 복구할 수 없고 초기화만 가능" 경고.
- 입력: 틀리면 "볼트 암호가 맞지 않습니다". **암호를 잊었어요** 링크 → 초기화 확인.
- 초기화 확인: "모든 클립(고정 포함)이 삭제됩니다" → 새 암호·확인 → `POST /api/vault/reset` → 저장.
- PBKDF2는 EDT 밖에서 돌리고 버튼에 "확인 중…" 표시.

### 5.3 트레이 메뉴

- "볼트 암호 변경…": 현재 암호·새 암호·확인. 현재 암호로 서버의 감싼 키를 풀어 확인한 뒤(자리 비운 PC에서 남이 바꾸지 못하게) 같은 VK를 새 KEK로 감싸 `PUT`.
- 로그아웃 시 저장된 볼트 키 삭제.

### 5.4 볼트 잠김 상태 (입력 창을 닫음)

- 복사해도 업로드하지 않는다. 툴팁에 "볼트 잠김".
- 최근 클립을 열면 입력 창을 먼저 띄운다.

### 5.5 업로드·받기

- 텍스트: 암호화 + HMAC → `POST /api/clips` (헤더 `X-Vault-Version`).
- 이미지: PNG(기존) → 썸네일 생성 → 원본·썸네일 각각 암호화 + 원본 HMAC → multipart `POST /api/clips/image`.
- 409 응답: 볼트 키를 버리고 입력 창. 그 업로드는 버린다(클립보드엔 그대로라 다시 복사하면 됨).
- 받기: 목록·푸시·썸네일·원본 모두 `e2e`면 앱에서 복호화 후 기존과 똑같이 표시/복사.
  복호화 실패 항목은 "🔒 열 수 없는 클립"(복사 불가, 삭제 가능).
- `ApiClient`에 multipart 본문 작성 도우미 추가(경계 문자열 + 파트, JDK `HttpClient`).

### 5.6 기존 데이터 이전

볼트를 쓸 수 있게 될 때마다 백그라운드로:
1. `GET /api/clips?legacy=true` (평문으로 옴)
2. 클립마다: 텍스트는 암호화 + HMAC, 이미지는 `/image`로 원본을 받아 썸네일 생성 후 둘 다 암호화 + HMAC
3. `PUT /api/clips/{id}/e2e`
4. 빈 목록이 올 때까지 반복. 개별 실패는 건너뛰고 다음 실행 때 재시도. 409·볼트 잠김이면 중단.
5. 옮긴 개수가 1 이상이면 알림 한 번: "기존 클립 N개를 종단간 암호화로 옮겼습니다".

## 6. 오류 처리 요약

| 상황 | 처리 |
|---|---|
| 볼트 암호 틀림 | GCM 태그 실패 → 안내 후 재입력 |
| 업로드 409 | 키 버리고 입력 창, 그 업로드는 버림 |
| 구버전 앱 | 볼트 없으면 옛 방식 허용, 있으면 426 |
| 서버 입력 오류 | base64·해시·크기·가로세로 → 400/413 |
| 복호화 실패 클립 | 🔒 표시, 복사 불가, 삭제 가능 |
| DPAPI 실패 | 저장된 키 없음으로 취급 → 입력 창 |
| iterations < 100,000 (서버가 준 값) | 앱이 거부, 오류 표시 |
| 이전 중 버킷 실패 | 503, 행은 옛 상태, 다음 실행 때 재시도 |

**남는 위험** (TRD에 기록)
- 서버 유출 시 감싼 키 + salt로 오프라인 암호 대입이 가능하다. PBKDF2 60만 회와 8자 이상으로 늦출 뿐이니 긴 암호를 권장한다. `GET /api/vault`는 device 토큰이 필요해 외부인은 감싼 키를 받을 수 없다.
- 메타데이터는 서버가 본다.
- 구버전 앱만 쓰는 사용자의 고정 옛 클립은 서버 암호화로 계속 남는다 → 서버 AES 키 제거는 별도 작업.

## 7. 테스트

**트레이 앱 단위 테스트**
- `VaultCryptoTest`: 감싸기/풀기 왕복, 틀린 암호·다른 userId(AAD) 실패, 텍스트·바이트 왕복, AAD 종류 불일치 실패, HMAC 결정성·키 의존성, iterations 하한 거부.
- `ImagesTest`: 썸네일 크기(긴 변 240, 작은 원본은 그대로, 비율 유지).
- `VaultTest`: DPAPI 저장/로드/삭제 왕복 — `@EnabledOnOs(WINDOWS)` (CI는 리눅스).

**백엔드 통합 테스트**
- `VaultApiTest`: GET 404 → POST 201 → POST 409 → GET 값 일치 → PUT version 불일치 409 / 일치 204 → reset 시 클립·객체 삭제와 version +1, 입력 검사 400, 남의 볼트 접근 불가(자기 것만).
- `E2eClipApiTest`: 헤더 규칙(없음+볼트 없음 허용, 없음+볼트 있음 426, 버전 불일치 409), 텍스트 e2e 저장값 = 보낸 값(서버 가공 없음), 목록·푸시에 `e2e=true`와 암호문, 이미지 multipart 저장 바이트 = 보낸 바이트, 크기 413, 가로세로 400, 중복 200.
- `MigrationApiTest`: `legacy=true` 목록(옛 행만, 평문), `PUT /{id}/e2e` 후 created_at·expires_at·pinned 유지와 e2e=true, 두 번 보내도 204, 이미지 덮어쓰기, 남의 클립 404.
- 기존 테스트: `Api` 도우미가 볼트를 만들고 `X-Vault-Version`·가짜 암호문으로 업로드하도록 변경. "서버 복호화"를 확인하던 테스트는 옛 행 경로(헤더 없음 + 볼트 없음) 테스트로 유지.

**실제 흐름 (로컬 Docker, 두 클라이언트 하네스)**
- A 볼트 생성 → B 입력 → A 텍스트·이미지 복사 → B 복호화 확인.
- 옛 행이 있는 사용자 → 볼트 생성 후 이전 확인(텍스트·이미지·고정 유지).
- 암호 변경 후 B 정상 동작, 초기화 후 B 업로드 409 → 입력 창.

**UI**: 볼트 창 4종(만들기, 입력, 변경, 초기화 확인)과 메뉴를 오프스크린 렌더링 스크린샷으로 확인받는다.

## 8. 배포

1. 백엔드 머지 → 자동 배포. 구버전 앱은 볼트가 없으므로 계속 동작한다.
2. 트레이 앱 v1.6.0 릴리스. 업데이트한 PC에서 볼트를 만들면 그 사용자의 구버전 PC는 426을 받는다(업데이트 알림으로 유도).
3. 확인: 운영 서버 대상 두 클라이언트 E2E.

## 9. 넣지 않는 것 (YAGNI)

- 복구 코드, 기기 승인 방식 키 전달
- 메타데이터 암호화(가로세로·크기 숨기기)
- 볼트 암호 강도 측정기 (8자 이상만)
- KDF 반복 횟수 자동 상향 (서버에 저장해 두므로 나중에 가능)
- 서버 AES 키와 옛 경로 제거 (옛 행 0개 이후)
